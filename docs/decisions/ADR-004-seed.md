# ADR-004: Deterministic seed and import fixtures (Phase 1, slice 4)

- Status: accepted
- Date: 2026-10-21
- Context: spec §31 (fake seed data), §30 (fixture-based import tests), §40.4, §42 rule 10

## Decisions

1. **One generator for the demo and Supabase.** `pnpm db:seed` (`supabase/seed/seed.ts`)
   loads the same deterministic world as the Phase 0 demo (`lib/db/demo/seed.ts`, fixed
   Faker seed, one random stream per shop). The pure mapping `supabase/seed/rows.ts`
   turns it into rows of the current schema and is unit-tested
   (`tests/unit/seed-rows.test.ts`): spec §31 sizes, distributions, determinism and
   tenant integrity. The demo presentation numbers stay guarded by `seed.test.ts`.
2. **Only tables that exist are seeded.** Schema v1 has companies, customers,
   vehicles, visits and service category mappings. The rest of the spec §31 profile
   ships with the slice that creates the table, from the same world:
   - suppression list (3 % suppressed): slice 13;
   - Dvořák's finished campaigns with results: slices 10, 12 and 14;
   - Horák's failed import: slice 7.
3. **Lifecycle columns come from visits only.** "Reactivated" and "opted out" need
   conversions and suppressions, which do not exist yet. The lifecycle job (slice 8)
   takes over the recomputation.
4. **Idempotent by fixed IDs.**
   - The seeded companies keep the same UUIDs and are deleted, with their data by
     cascade, then re-created.
   - Dates are relative to the moment of seeding; the people, vehicles and history
     are identical on every run.
5. **Seeded accounts:**
   - One platform admin, `operator@navrat.example.cz`.
   - For each shop, an owner (`majitel@…`) and a manager (`vedouci@…`).
   - The password is `SEED_USER_PASSWORD`, which `pnpm env:local` generates once into
     the gitignored `.env.supabase.local`, so no password is committed.
   - Re-seeding resets these accounts to that state: password, memberships and no MFA
     factors. The operator therefore enrols TOTP again; the E2E suite relies on this.
6. **Local only.** The seed refuses any Supabase URL other than localhost, and
   `APP_ENV=production`, the same as `admin:create`.
7. **Import fixtures** are generated by `supabase/seed/fixture-files.ts`
   (`pnpm db:fixtures`) and committed in `supabase/seed/fixtures`, together with
   `manifest.json`. The manifest records each file's ground truth: row counts,
   duplicates and malformed values with their row numbers. The generator uses a fixed
   PRNG and fixed dates, so its output is byte-identical; `tests/unit/fixtures.test.ts`
   fails if the files drift. The files:
   - a Windows-1250 `;` CSV with dd.mm.yyyy dates and "4 700 Kč" prices (plain and
     no-break spaces, ",00", empty values, quoted notes);
   - a two-sheet XLSX with real date cells, numeric phone cells, a blank row and a
     "Celkem" summary row with a SUM formula;
   - a UTF-8 CSV with a BOM, exact duplicate rows, six kinds of malformed phone and an
     invalid date;
   - a ragged, unclosed-quote CSV and a truncated XLSX.
     Slice 7 asserts the import results against the manifest. SheetJS (official CDN
     tarball) and iconv-lite are dev dependencies until the import slice uses them at
     runtime.
8. **Czech name collation.**
   - Migration `20261021120000` sorts `customers.first_name` and `last_name` with an ICU
     `cs-CZ` collation (`app.czech`) and adds a `(company_id, last_name, first_name, id)`
     index for the paginated list.
   - PGlite has no Czech ICU data. It creates the collation with root rules, so the
     no-Docker test runner checks that the collation is attached but not the Czech
     order.
9. **Real-data screens for the slice's demo target** (`lib/real-data-routes.ts`):
   - the companies list, with links and customer counts;
   - a company header with its profile;
   - a read-only customer list with 50 rows per page, for the operator per company and
     for shop users at `/app/customers`.
     Queries run through the user's RLS session with an explicit `company_id`. Search,
     filters and the customer detail come in slice 6.

## Consequences

- The pgTAP tests no longer assume an empty database. Counts are scoped to the tests'
  own fixtures, because `supabase test db` may run on a seeded stack.
- CI seeds the stack before the Supabase E2E suite.
